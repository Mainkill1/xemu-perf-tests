# Morrowind fixed-snapshot Vulkan latency: current diagnosis

This diagnosis uses product PR #87 head `974f2ae63b166f64aa2ea6a77963c77481e28969`, its exact #85 parent `2163208fdc49c7f6b4834bce98e6a11b494d4241`, and the pinned `vm-20260905015459` snapshot. The observed cadence counts NV2A **guest display writes**, not host-presented FPS. The camera is fixed, so the result does not cover travel through Morrowind's map. The longer [PR #87 report](REPORT.md) and the [earlier #86 source/trace investigation](https://github.com/Mainkill1/xemu-perf-tests/blob/evidence/pr85-vertex-surface-freshness/docs/evidence/pr85-vertex-surface-20260912/issue86-deep-diagnosis/REPORT.md) retain the source and build identities for each probe.

The renderer's source explains the sequence. A dirty vertex range that an earlier recorded draw may still read enters `pgraph_vk_update_vertex_ram_buffer()`; its staged path calls `pgraph_vk_begin_nondraw_commands()`, ending an active render pass before barriers and `vkCmdCopyBuffer()`. A later draw begins a new pass and binds the necessary state. At descriptor capacity, `update_descriptor_sets()` calls `pgraph_vk_finish(... NEED_BUFFER_SPACE)`, which submits the auxiliary and main command buffers, waits for their fence, and only then recycles descriptors and staging space. At FIFO idle with a queued report, the report path may call `pgraph_vk_finish(... STALLED)` before publishing the report. Removing either fence without preserving resource ownership and the guest's completion contract would change behavior, not merely remove overhead.

### Direct guest-to-report address match

One **trace-only diagnostic build** applied the [small report-address patch](profiling/report-address-diagnostic.patch) to the exact #87 product tree; its Windows executable SHA-256 is `0fbd3b777fc9d040a1a98ef7555fc6bea0a0a3653c6f51fee8c801b409667894`. The [QMP sampler](profiling/sample-report-address.ps1) used the previously inspected helper's index lookup, read the index from the live helper stack when sampled at its entry, and called `gva2gpa` on the derived record. The diagnostic run reached the fixed snapshot, completed a 15-second window with **361 guest display writes**, passed the final-image check, preserved the seed, deleted its private disk, and left no xemu/tracing process. These are address and ordering observations, **not** performance timings for comparison with product builds.

All **538** complete-run report triplets used that same destination and had zero queries. Of 180 QMP register samples, nine resolved the record and two transiently reported it unmapped; the nine resolved reads saw completion word zero. QMP monitor servicing occurred after publication in those samples, so this run **does not timestamp the first pending guest load** or prove that the entire earlier `NEED_BUFFER_SPACE` wait was spent inside the guest retry loop. It does close the previously open destination-identity question. The [compact trace summary](results/morrowind-pr87-report-address-match.json) records exact source/build/runner identities and hashes of private raw inputs; no game code, RAM dump, or private disk is published.

The 1→2→1 surface-scale control did not materially change uninstrumented guest cadence (**24.642→25.170→25.565 writes/s**), while main-GPU median in separate diagnostic cells rose **5.75%** at scale 2. This weakens a simple pixel-fill explanation for the fixed-view throughput limit. A same-executable Vulkan→OpenGL→Vulkan return control measured **25.613→34.383→25.364 guest writes/s**. OpenGL's zero-query report path can publish without Vulkan's command-buffer fence; the return control therefore cannot establish that OpenGL executes the same GPU work 35% faster. Direct OpenGL GPU intervals and host-presented frames were not captured.

The earlier counter probes also narrow alternate explanations: **82.5%** of descriptor updates changed effective image/sampler handles; there were no immediately repeated identical recorded descriptor-set binds. A warmed 243-write window created only **20** graphics pipelines, and none of its requested pipeline keys differed solely in the tested alpha-reference or polygon-offset uniform values. Repeated *new* shader or pipeline compilation is not the established cause of this steady fixed-scene wait. These measurements were on the older same-scene diagnostic tree, so their exact counts require refresh if used to justify a current-head patch.

## What is still missing for a definitive fix

The measured bottleneck is **GPU completion of many small, frequently interrupted Vulkan draw batches, exposed to the guest through a report record that now has a direct physical-address match**. Two causal details remain open: the exact current-head GPU time attributable to ordered vertex-copy pass breaks versus necessary draw/state work, and the timestamp of the guest's first pending read relative to submission and publication. The current evidence supports #87's bounded fresh-page change, which gains about 6% here, but does not justify promising a 35% or 2× gain from it.

The next diagnostic should timestamp the guest's **first pending completion-word load** against submit/fence/publication; ordinary QMP polling observed the completed word too late. In a separate opt-in current-head GPU probe, sample render-pass/copy boundaries and draw batches at a bounded rate to estimate their cost without attributing every query-instrumented nanosecond to production. Keep diagnostic cells separate from uninstrumented performance cells. A subsequent product experiment can use versioned vertex ranges or earlier ordered execution only after proving that earlier draws keep their old bytes, later draws see updates, and reports become visible after required GPU completion. Test against exact previous main and the fixed baseline; preserve the full XISO and game oracles.

**Scope of confidence:** The fence-to-GPU-batch match, current-head parent comparison, and guest/report destination match are measured on exact #87 identities. The helper's code interpretation and per-draw/pass counts come from earlier same-scene diagnostic trees. No displayed-FPS, native OpenGL GPU-timestamp, first-pending-load timestamp, game-wide traversal, or safe asynchronous-report result is claimed.
