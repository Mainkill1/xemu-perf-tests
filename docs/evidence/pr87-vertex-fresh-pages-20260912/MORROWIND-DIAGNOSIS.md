# Morrowind fixed-snapshot Vulkan latency: current diagnosis

This diagnosis uses product PR #87 head `974f2ae63b166f64aa2ea6a77963c77481e28969`, its exact #85 parent `2163208fdc49c7f6b4834bce98e6a11b494d4241`, and the pinned `vm-20260905015459` snapshot. The observed cadence counts NV2A **guest display writes**, not host-presented FPS. The camera is fixed, so the result does not cover travel through Morrowind's map. The longer [PR #87 report](REPORT.md) and the [earlier #86 source/trace investigation](https://github.com/Mainkill1/xemu-perf-tests/blob/evidence/pr85-vertex-surface-freshness/docs/evidence/pr85-vertex-surface-20260912/issue86-deep-diagnosis/REPORT.md) retain the source and build identities for each probe.

The renderer's source explains the sequence. A dirty vertex range that an earlier recorded draw may still read enters `pgraph_vk_update_vertex_ram_buffer()`; its staged path calls `pgraph_vk_begin_nondraw_commands()`, ending an active render pass before barriers and `vkCmdCopyBuffer()`. A later draw begins a new pass and binds the necessary state. At descriptor capacity, `update_descriptor_sets()` calls `pgraph_vk_finish(... NEED_BUFFER_SPACE)`, which submits the auxiliary and main command buffers, waits for their fence, and only then recycles descriptors and staging space. At FIFO idle with a queued report, the report path may call `pgraph_vk_finish(... STALLED)` before publishing the report. Removing either fence without preserving resource ownership and the guest's completion contract would change behavior, not merely remove overhead.

### Direct guest-to-report address match

One **trace-only diagnostic build** applied the [small report-address patch](profiling/report-address-diagnostic.patch) to the exact #87 product tree; its Windows executable SHA-256 is `0fbd3b777fc9d040a1a98ef7555fc6bea0a0a3653c6f51fee8c801b409667894`. The [QMP sampler](profiling/sample-report-address.ps1) used the previously inspected helper's index lookup, read the index from the live helper stack when sampled at its entry, and called `gva2gpa` on the derived record. The diagnostic run reached the fixed snapshot, completed a 15-second window with **361 guest display writes**, passed the final-image check, preserved the seed, deleted its private disk, and left no xemu/tracing process. These are address and ordering observations, **not** performance timings for comparison with product builds.

All **538** complete-run report triplets used that same destination and had zero queries. ### GPU interval around ordered vertex uploads

A second **trace-only** build applied the [GPU-span diagnostic patch](profiling/vertex-upload-gpu-span-diagnostic.patch) (SHA-256 `9cbce4f8a3a37262eb561b2da424270ae135aed1a9dc5fde3788c888235a820e`) to the same exact #87 source. Its executable SHA-256 is `466c15c31c0e882f506fef38a06facd984f7d4113c0b39126e728a425e5b3338`. Each timestamp pair starts before the staged upload enters nondraw commands, where an active render pass is ended, and stops after its barriers and `vkCmdCopyBuffer`. It **excludes the next render-pass begin and draw rebind**. The query pool allows 256 pairs per submission; none overflowed. This changes the measurement workload and is not a performance A/B.

All **57,707** timed uploads entered with an active render pass. The `NEED_BUFFER_SPACE` median upload span was **1.214 ms per guest write**, p95 **2.408 ms**. Across its 251 writes, upload span and main-GPU time had rank correlation **0.929**; the fastest and slowest main-GPU deciles had median upload spans **0.836 and 2.303 ms**, respectively. ### Separate render-pass versus ordered-copy span probe

To classify the remainder, a **new trace-only build** on the same exact product head timestamped every render pass immediately before `vkCmdBeginRenderPass()` and after `vkCmdEndRenderPass()`. It also moved the copy pair's start to **after** the pass ended, so the two interval classes do not overlap. The [diagnostic patch](profiling/pass-and-copy-gpu-span-diagnostic.patch) SHA-256 is `affc23a35342a794fac77822e49b7e7e843a82630028c2973909d5b5acb4f147`; the Windows executable SHA-256 is `b448bde92ea90ce88d37c85b6f29245a34ae7dd966f4479b836565e674dc36ba`. A single 10-second fixed-snapshot Vulkan window recorded **243 guest display writes**, passed its final-image check, kept the snapshot seed unchanged, deleted its private disk, and closed xemu and all trace processes. Its diagnostic cadence was **24.287 writes/s**; it is **not** compared with uninstrumented product timing.

| Timed interval in the new 243-write diagnostic | `NEED_BUFFER_SPACE` | All finish reasons | Share of all main-GPU time |
| --- | ---: | ---: | ---: |
| Entire main command buffer | 2,060.082 ms | 2,317.986 ms | 100.00% |
| Render passes: begin through end, including draws | 1,527.530 ms | 1,711.548 ms | **73.84%** |
| Ordered staged copies: barriers and copy, after pass end | 348.672 ms | 375.501 ms | **16.20%** |
| Outside both timestamp-pair classes | 183.880 ms | 230.937 ms | **9.96%** |
| Timed render passes / ordered copies | 55,080 / 54,338 | 61,718 / 57,702 | No query overflow |

Within `NEED_BUFFER_SPACE`, render-pass span and main-GPU time had rank correlation **0.982** across 243 writes; median pass span was **5.944 ms**, p95 **8.878 ms** per write. The run averaged about **254 render passes** and **237 ordered staged copies** per guest display write. These measurements place most of the instrumented main-batch delay **inside frequently restarted render passes**, with another meaningful share in the ordered copy path. A render-pass span includes pass begin/end, draws, and any commands between them; it does **not** isolate shader execution, pipeline binding, attachment cost, or a removable restart penalty. Query commands may change all of those intervals. The new [compact result](results/morrowind-current-head-pass-and-copy-gpu-span.json) records the alignment, zero overflow, every finish reason, exact identities, and hashes of private raw inputs. Do not combine its totals with the earlier upload-only diagnostic as though they were one run.

The 1→2→1 surface-scale control did not materially change uninstrumented guest cadence (**24.642→25.170→25.565 writes/s**), while main-GPU median in separate diagnostic cells rose **5.75%** at scale 2. This weakens a simple pixel-fill explanation for the fixed-view throughput limit. A same-executable Vulkan→OpenGL→Vulkan return control measured **25.613→34.383→25.364 guest writes/s**. The first Vulkan and OpenGL rates correspond to about **39.043 and 29.084 ms per guest write**, a **9.959 ms** gap. That is numerically close to the separate four-timestamp Vulkan run's **9.674 ms median `NEED_BUFFER_SPACE` fence wait per write**, but it is not a measured one-for-one causal saving: the renderers do different work and may overlap it differently. OpenGL's zero-query report path can publish without Vulkan's command-buffer fence; the return control therefore cannot establish that OpenGL executes the same GPU work 35% faster. Direct OpenGL GPU intervals and host-presented frames were not captured.

The earlier counter probes also narrow alternate explanations: **82.5%** of descriptor updates changed effective image/sampler handles; there were no immediately repeated identical recorded descriptor-set binds. A warmed 243-write window created only **20** graphics pipelines, and none of its requested pipeline keys differed solely in the tested alpha-reference or polygon-offset uniform values. Repeated *new* shader or pipeline compilation is not the established cause of this steady fixed-scene wait. These measurements were on the older same-scene diagnostic tree, so their exact counts require refresh if used to justify a current-head patch.

## What is still missing for a definitive fix

The measured Vulkan-specific bottleneck is **GPU completion of many small, frequently interrupted draw batches, exposed to the guest through a report record that now has a direct physical-address match**. The new same-head diagnostic places **73.84%** of main-GPU time inside render passes, **16.20%** around ordered copies, and **9.96%** outside those disjoint intervals. Although the GPU intervals sum to only **2.318 s** over a 10-second window, roughly one completion is required per guest write; serial waiting can constrain cadence without 100% aggregate GPU busy time. The timestamp of the guest's first pending read relative to submission and publication remains unknown. The current evidence supports #87's bounded fresh-page change, which gains about 6% here, but does not justify promising a 35% or 2× gain from it.

The next diagnostic should timestamp the guest's **first pending completion-word load** against submit/fence/publication; ordinary QMP polling observed the completed word too late. Within the dominant render-pass interval, distinguish useful draw execution from pass setup/restart at a bounded sampling rate before promising a particular saving. Keep diagnostic cells separate from uninstrumented performance cells. A subsequent product experiment can use versioned vertex ranges or earlier ordered execution only after proving that earlier draws keep their old bytes, later draws see updates, and reports become visible after required GPU completion. PR #85's newly reviewed fetch-span/readback-ordering gaps must be corrected and #87 rechecked before integration. Test against exact previous main and the fixed baseline; preserve the full XISO and game oracles.

**Scope of confidence:** The fence-to-GPU-batch match, current-head parent comparison, and guest/report destination match are measured on exact #87 identities. The helper's code interpretation and per-draw/pass counts come from earlier same-scene diagnostic trees. No displayed-FPS, native OpenGL GPU-timestamp, first-pending-load timestamp, game-wide traversal, or safe asynchronous-report result is claimed.
